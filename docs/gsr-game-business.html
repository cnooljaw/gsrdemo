01 · 看懂业务GSR 1.0.4 · gsrdemo

一个玩家打地鼠的完整流程

进入、即时命中、持久入账：三段路径，各有成功边界。

accepted 是内存接纳；committed 才是最终入账。
用 GSR 构建游戏业务02 / 21

先讲两阶段：PasswordAuth 1003 → AuthService 验证密码 → TokenService 签发 Redis Token；Login 1001 → TokenService 校验 → Online.Bind，成功才开放游戏。认证只发凭据，不绑定 Online；客户端不传 UserID/LoginID/节点地址。

进入：Agent 直接 Call 固定名称 mole-entry，名称和命令来自 moleentry 共享契约；Entry 核对 Online，通过 Accounting / 6 复用缓存，明确缓存缺失时才向 settlement-read / 4 查询余额。每次选入尝试生成独立 Membership 并恢复余额，再由目录预留、Join 原组。确认原组停止后重选时重新建立身份和余额视图，旧组的迟到回收不影响新组；Join 超时保留原路由，不自动换组。

地鼠每组最多 3 人、9 洞，有人即可玩；每秒产生一个目标，有效 2 秒。每锤扣 100，返 0 或 198 各 50%。同目标只允许一人命中，原 ActionID 的重复内容返回原结果，奖励固定一次。

Accounting 不做外部 I/O：100ms/数量/字节阈值归批，单缓冲、单在途批次，最多 4096 项待确认。Submission 用 restoreCheckpoint 恢复；submitBatch 保存原批次后 Call settlement-write / 1，校验返回回执后直接 completeBatch，Redis 更新确认统计并清除待批次后才交付 Accounting。Call 有限等待 3 秒，只占用 Submission；超时或临时错误原 ID 退避重试，永久错误暂停新记账，未知命令和参数不匹配也按接线错误暂停，修复后重启恢复原请求。Redis 确认失败保留已收到的回执，不重复调用结算。

余额校正走 Accounting → MoleService → AttackService → Agent 102 → 1062。结果一致不重复奖励。客户端不查询逐锤入账，余额校正由回执直接触发。离开不取消已接纳操作。正常离开、确认停止后的整组清理，以及目录明确拒绝且未建立用户路由的预留尝试，均由目录保留未接纳的缓存回收通知，复用 Pulse 限量补投；Accounting 按 Membership 忽略迟到通知，有待结算操作时等回执完成再回收。未保存 Redis 的内存命中可因崩溃丢失。

01 · 看懂业务GSR 1.0.4 · gsrdemo

三个玩家斗地主的完整流程

牌局结束直接结算，三人各收一次最终结果。

局末直接结算再给结果；Redis 只保存待恢复请求。
用 GSR 构建游戏业务03 / 21

三名不同账号可以在同一个 access，也可以跨两个 access。LandlordService 优先补满可入座桌；Resolve 生成的未入座预留有效 30 秒，迟到 Join 拒绝过期 Membership。进入者随后直达该桌，不逐次经过目录。

Ready 读取权威余额，至少 20 银子只是准入预判，不冻结资金。三人准备后每人 17 张，另留底牌 3 张；随机首叫，按经典叫抢流程确定地主。

出牌循环只对当前轮次有效。快照由服务端按本人生成：本人手牌、其他人余牌数，确定地主前隐藏底牌。

正常局末不广播 finished + pending。先保存本游戏 Redis Hash，再由本桌 Call settlement-write / 7；GSR 路由至池成员，等待只占用本桌，其他桌继续工作。输方最多扣至 0，赢家均分实际扣款，余数按 UserID 从大到小分配；牌局胜负不变。收到有效回执后向三人各推送一次最终结果，再清理 Redis；删除失败只重试清理，三人全离开后仍完成清理再退出。

Redis 只为已保存局末请求提供故障恢复，不保存成功历史、不用于提高 SQL 吞吐。结算服恢复后原 ID 重试；地主节点重启补交原请求，SQL 已提交时幂等返回原回执。客户端使用终态快照，不再请求 1151 查账。Call 结果未知时内部保留 pending，主动查询桌快照仍可看到待确认，不把超时当作失败或成功。确定性错误暂停原请求，临时故障和坏回执退避重试；具体边界见 斗地主恢复设计。不恢复进行中手牌，旧 LoginID 的操作和推送仍被过滤。

02 · 理解 GSRGSR 1.0.4 · gsrdemo

Actor 思想：状态有唯一的主人

先回答“谁能修改这份状态”，再决定如何拆 Service。

别的 Service 请求它做事；它在自己的消息回调里完成状态变化。
用 GSR 构建游戏业务04 / 21

Actor 是理解方法，实际 API 使用 GSR 的 Service、Send、Call 等术语。一个 Service 是运行单元，有自己的 Mailbox 和串行执行边界。

桌内的 attackGame 和 roundSettlement 是 owner 私有对象，通过普通方法调用协作；外部 Service 不保存其指针，更不能越过 Mailbox 修改手牌。

所有权要求也适用于消息中的 map/slice。发送专用快照，成功接纳后不再修改；返回值不能暴露内部可变状态。

MySQL 是持久账务权威，多结算节点访问同一库的并发一致性由事务、行锁和唯一键保障；不要把进程内 owner 约束误讲成数据库只能有一个访问者。

Actor 思想在 GSR 中的表现

Service 是执行边界，普通对象是代码组织方式。

独立运行单元Service + Mailbox + 串行 Handler
发送消息 / 等待结果Send / 有限等待的 Call
计时与生命周期After 投递 Command；OnStart / OnStop
身份与地址业务 ID；本地 ServiceID；节点内 ServiceName

GSR 当前每个运行 Service 由 Runtime-owned runner 串行消费 Mailbox。业务无需也不应启动 goroutine 来绕开边界。

03 · 跨节点协作GSR 1.0.4 · gsrdemo

Cluster：消息如何到达另一个节点

业务按名称寻址，框架负责编码、连接与投递。

NodeID 选择节点；ServiceName 选择服务；CommandID 选择该服务的业务入口。
用 GSR 构建游戏业务08 / 21

节点表来自 configs/nodes.yaml。OpenCluster 按目标条目的端口监听，接受入站；主动 Send/Call 不要求调用方先开放自己的监听。

远程请求解析目标服务的当前临时 ID，再走目标 Runtime Mailbox。跨节点 Core Source 为零，不能用它代替玩家身份；需要 UserID/LoginID 等业务字段并校验。

每个目标节点共享出站发送 owner/连接。请求和响应分帧，回复沿原连接，反向主动推送是另一个出站调用。连接按需建立并可恢复，已失败/未知业务不会自动重放。

名称随目标 Service 停止而清理，创建者退出不会撤销名称。稳定业务身份、LoginID、OperationID 不要与 Runtime Session 或 ServiceID 混为一谈。

Cluster：业务应该如何调用

调用签名和错误边界，就是节点之间的业务契约。

Go · roundSettlement.submit 的 Call 片段
ctx, cancel := context.WithTimeout(
    context.Background(), settlementCallTimeout,
)
value, err := self.Cluster().Call(
    ctx, round.node,
    settlementwrite.ServiceName,
    settlementwrite.SettleEqualGroupCommand,
    round.operation.wire(),
)
cancel()

有界等待

仅本桌等待，其他桌继续处理。

规范类型

int64 / uint64 / []any / map[string]any

回执校验

直接核对原 ID、终态与三人余额。

本地消息不编码；跨网会规范化类型。两种调用共用 Handler 时统一参数类型。
用 GSR 构建游戏业务09 / 21

此片段来自 roundsettlement.go 的直接 SettleEqualGroup；省略了先保存 Redis、错误分类、退避检查和 applyReceipt。服务名与命令引用 settlementwrite 生成契约，不能在调用处再抄字符串和数字；生成器不验证参数顺序、结果或完整接线。Call 等待 2 秒，Redis 保存和删除各 250ms，与 access 的 3 秒外层等待留出余量；不包含桌邮箱的先前排队。超时仍可能已入账，Pulse 从本次等待结束后至少间隔 1 秒再按原 ID 重试。

默认 ValueCodec：有符号数 → int64，无符号数 → uint64，浮点 → float64，普通列表 → []any，字符串键 map → map[string]any；[]byte 保持二进制。struct/指针不直接跨网编码。

Dispatcher 只按签名检查最外层类型，不做隐式数值转换或元素/字段业务校验。本地 Args 仅浅拷贝，发送者仍须构造独立快照；返回值同样不能暴露 owner 内部引用。

当前回调校验业务 ID、完整回执和钱包版本，终态确认后不再调用结算。斗地主在保存和 Call 报错处区分确定性错误与临时故障，命令不存在或参数不匹配也会暂停；坏回执仍是未知结果，继续退避重提原请求。完整规则见 斗地主恢复设计。

gsrdemo 的业务代码规范

让调用入口、状态归属和失败行为都能直接从代码读出来。

边界写法为什么
状态每份可变状态一个 owner；纯规则用普通对象让修改入口可见
Service显式 Handle；具名 Dispatcher；类型后接口断言让角色与分发接线可见

用 GSR 构建游戏业务11 / 21

以 Service 决定公开范围；不同 Service 可以复用命令编号。

Go · mole/attackservice.go 命令定义

const (
    attackJoinCommand     runtime.CommandID = 1
    attackHitCommand      runtime.CommandID = 2
    attackSnapshotCommand runtime.CommandID = 3
    attackLeaveCommand    runtime.CommandID = 4
    attackTickCommand     runtime.CommandID = 10
    attackBalanceCommand  runtime.CommandID = 11

整 Service 标记公私

public 生成全部命令；private 不生成。标记不提供网络隔离。

源定义是唯一维护处

./scripts/dev.sh generate rpc
跨节点引用生成的命名常量。

名称跟随实际寻址

固定入口或池：生成 ServiceName。
动态实例：只生成命令。

生成只同步名称和编号；参数、结果与完整 Handler 接线仍需验证。
用 GSR 构建游戏业务12 / 21

命令定义在 Service 文件或附近；每个 Service 独立命令块，编号显式赋值并在块内唯一。客户端 MsgID 属于另一编号空间。每个公开 Service 的全部命令整体生成，不再逐条标记公私。

运行 ./scripts/dev.sh generate rpc，从该块生成 common/rpc/moleattack/commands.gen.go。源常量 attackHitCommand 对应生成的 moleattack.AttackHitCommand。同节点优先使用源定义，跨节点调用方引用生成契约；不要手改产物。契约包名对应实现名，例如 moleattack 和 landlordattack 对应各节点的 AttackService。

固定名称可参考 moleentry：标记为 //rpc:service moleentry public name=moleEntryName，名称字符串与命令定义在同一块。动态组省略 name=，使用进入结果返回的 AttackName；服务池只生成池的逻辑名称，不暴露成员 ID 或数量。私有 Pulse 可参考 //rpc:service molepulse private；业务调度配置放在命令块之外。

Dispatcher 仍手工将 ID 绑定 handle 方法，Service 显式 Handle 转发；客户端协议绑定 on 方法。生成器不检查参数顺序、返回类型、完整 Handler 接线；check 只读检查生成同步。参数与回执校验、真实通信测试仍必需。

服务池在启动时创建多个独立 Service，各自串行处理邮箱，成员之间并行。某个成员等待慢 SQL 时，其他成员可以继续处理；调用方只 Call settlement-write，由 GSR 选择成员并返回回执，不需要自己分配执行者或注册回调。单个调用方连续同步 Call 仍逐笔等待。

07 新节点补 YAML、nodes.yaml 和现有 dev.sh 的节点支持，不新增重复脚本。按实际需要调用结算命名契约并校验回执；确定原 OperationID/BatchID、金额及恢复承诺后再重试。客户端不逐笔轮询账务，已保存请求的恢复和成功后的清理由业务明确处理。

08 先相关规则与失败用例，再执行 ./scripts/dev.sh check；修改后构建并运行实际通信闭环。check 只读检查名称编号同步，不能证明参数顺序、返回类型或完整接线正确；逐项验证非法参数、旧 LoginID、路由、重复/冲突、超时未知和回执。涉及资金再核对实际扣返与最终账务；状态/生命周期/并发变化才对受影响包运行 race。

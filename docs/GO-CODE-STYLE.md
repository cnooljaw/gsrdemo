# GSR Demo Go 编码规范

目标是让熟悉业务、但不是原作者的开发者能够顺着代码理解流程、状态归属和失败处理。优先简单、直接、可验证的写法，不以行数、文件数或抽象层数衡量质量。

## 1. 适用范围

本规范补充 Go 官方约定，适用于本仓库手写的 Go 代码和测试；生成代码由固定版本的工具维护。第 2～4 节为执行规则，其中标明“优先”“按需”的条款允许根据实际场景取舍；第 5 节是评审建议，不作为机械门禁。

相关约定各有一个维护入口：

| 文档 | 负责内容 |
| --- | --- |
| [AGENTS.md](../AGENTS.md) | 工作流程、修改边界、版本与提交约定 |
| [DESIGN.md](DESIGN.md) | 节点职责、业务状态和恢复边界 |
| [PROTOCOL.md](PROTOCOL.md) | 消息编号、参数和结果契约 |
| [README.md](../README.md) | 环境准备与工程命令 |

GSR API 以实际依赖版本为准，参考入口见 [GSR 与参考边界](DESIGN.md#21-gsr-与参考边界)。本文件最初参考 GSR 编码规范 revision `b2a9f16ae78da0bade541eabbb39a9144d5e04d2`，现按本项目需要维护；框架内部的开发规则不直接套用到业务代码。

## 2. 书写与命名

### 2.1 文件与格式

- Go 代码经过 `gofmt`。函数之间留一个空行；具名函数使用多行函数体，每行表达一个主要动作，不用分号压缩流程。
- 文件按具体类型或职责命名，例如 `loginservice.go`、`agent.go`、`account_mysql.go`，避免含义过宽的 `service.go`。
- 同一类型确需拆文件时保留类型前缀，如 `agent_login.go`。独立职责优先通过具名字段组合，文件名前缀不代表所有方法都必须挂在同一个类型上。
- 长签名、调用和复合字面量按语义换行。约 120 字符是阅读提示，不是硬性长度限制。

### 2.2 名称表达实际行为

- 使用稳定的业务术语，区分操作、请求、回执和快照。名称应让调用者判断函数是在组装数据、修改状态、提交任务还是发送消息，例如 `snapshotFor`、`applyReceipt`、`submitBatch`、`pushSnapshots`。
- 避免 `data`、`obj`、`tmp`、`ret` 等缺少含义的名称；不同职责不要只靠大小写区分。access 的连接 Service 使用 Agent，内部组件按自身职责命名，不强制统一后缀。
- 缩写遵循 Go 习惯，如 `ID`、`URL`、`HTTP`、`RPC`、`GSR`。
- 同一类型的接收者名称保持一致，不用 `this` 或 `self`。普通 `context.Context` 参数用 `ctx`；`gsr.ServiceContext`、`gsr.CommandContext` 参数用 `self`；未使用的参数用 `_`。
- 消息入口的 `handle...`、`on...` 命名集中见 [消息注册与分发](#33-消息注册与分发)，普通业务方法不套用这些前缀。

### 2.3 控制流与错误

- 错误、无效输入和终止分支优先提前返回；已经 `return`、`continue` 或 `break` 的分支后，不写多余的 `else`。
- 只检查一次调用错误时，可以用 `if err := ...; err != nil`。返回值还参与后续判断时，拆成具名局部变量，不把错误、nil 和业务状态挤进同一个条件。
- 错误必须有明确处置方式。使用 `errors.Is`、`errors.As` 或稳定错误码判断，不匹配错误字符串；预期的业务失败和外部故障不使用 panic。
- 需要保留原因时用 `%w` 包装，并补充操作或关键身份；不要多层重复添加没有定位价值的 `failed`。清理阶段需要保留多个错误时，使用 `errors.Join` 等明确的聚合方式。
- 日志由能够决定处置方式的边界记录，避免每层既记录又返回同一个错误。尽力通知等允许失败的操作也要明确后果，不能把忽略错误当作默认写法。

```go
player, err := repository.LoadPlayer(ctx, playerID)
if err != nil {
	return fmt.Errorf("load player %d: %w", playerID, err)
}
if player.Disabled {
	return ErrPlayerDisabled
}
```

### 2.4 注释与文档

- 自然语言注释尽量用中文，说明契约、原因和非显而易见的限制，不复述代码。导出符号提供 Go doc，重点说明调用者需要知道的行为和失败语义。
- TODO 写清未完成事项；需要持续追踪时链接设计文档或任务。
- 需要包级说明时使用 `doc.go`；不为凑文件新增空说明，不在包文档中隐藏初始化或副作用。
- 可执行示例使用带语言标识的代码块，说明执行目录和必要前置条件。重复操作收敛到现有工程入口，不在多份文档复制维护。

## 3. 职责与 GSR 接入

### 3.1 类型、依赖与构造

- 依赖通过明确字段或参数传入；接口由使用者按实际边界定义。存在多实现、测试隔离或模块边界等需要时再引入接口，不为每个具体类型增加一层包装。
- 结构体优先具名组合。只有不会隐藏入口、所有权和生命周期时才使用匿名嵌入；纯规则与值对象不为对称关系强行拆成 Service。
- 组件持有自身职责需要的数据和依赖，不通过完整父 Service 指针任意访问其他组件。共享事实只有一个来源，通过参数或窄能力访问；确需读取最新状态时，再注入读取函数，不能长期把构造时的副本当作当前值。
- 构造函数建立对象必须满足的不变量，可能失败时返回 `error`。同一组件内部必须一致的依赖由构造保证，不要求每个调用方重复组装和校验。
- 明确承担接口职责的类型，在类型定义后紧跟编译期断言；多个接口集中放在一个 `var` 块。断言使用实际的方法集，生产实现与测试替身同样遵守；普通值对象无需人为增加接口。
- `MustXxx` 表示失败会 panic，只用于程序员定义的静态组装；外部输入、配置和运行故障使用普通错误返回。

### 3.2 状态、并发与生命周期

- 每份可变状态只有一个 Service owner。其私有组件由该 Service 串行调用，不因此获得独立 Mailbox、生命周期或并行能力；跨 Service 通过消息访问，引用参数和结果传独立快照。
- `self`、Node 和 Handler 上下文仅在当前回调内使用，不保存到对象，也不借给异步任务。`context.Context` 用于取消、截止时间和请求信息，不充当依赖容器；只有明确的生命周期 owner 才持有用于关闭的根 context/cancel。
- 业务层不启动 goroutine，异步流程使用消息、GSR Timer 或独立 Service。不要用锁或 channel 绕过 Service 的状态所有权。
- 确有 goroutine 的基础设施必须负责取消、等待退出、并发上限和错误归属。channel 只用于实际的通信或队列需要，不作为默认解耦手段。
- 周期唤醒按 GSR 的 `After` 与 Command 约定实现；状态仍由 owner 的 Handler 修改，投递失败和后续调度必须有明确处理。
- 资源由创建或显式接管它的 owner 关闭，业务不重复关闭 GSR 托管资源。`self.Exit()` 后立即返回；创建者退出不会自动停止已经创建的 Service。

### 3.3 消息注册与分发

- GSR 内部命令入口使用 `handle...`，客户端协议入口使用 `on...`；组件归属由类型或字段表达，不在每个方法名中重复游戏名。框架要求的 `Handle`、`HandleClientMessage`、`OnStart`、`OnStop` 保留原名。
- Service 显式实现 `Handle`；有业务命令时具名持有 Dispatcher 并转发，无业务命令的 MainService 返回 `ErrUnknownCommand`。客户端 Agent 另显式实现 `HandleClientMessage`，不依靠匿名嵌入提升入口方法。
- 不同业务消息使用独立 CommandID，直接绑定具体处理方法；不在通用 Handler 中用 `kind/type` 字符串建立第二套命令路由。普通玩法规则内部的条件分支不受此限制。
- 注册表每行一个“ID → 方法”，由 `gofmt` 对齐。CommandID 在同一 Service 合并后的表中唯一，不同 Service 可以复用；客户端 MsgID 属于另一个编号空间。重复注册和占用框架保留编号在组装时拒绝，不能按顺序覆盖。
- Service 名称、CommandID 等契约就近定义。有真实共享调用需求时才提取共享契约，不为少量常量新建通用层；节点不导入彼此实现。
- 固定组件显式组装，不按每条消息重建，也不引入自动发现框架。access 的通用协议与各游戏分别提供注册表，由同一份组件清单汇总注册、进入互斥和断线清理；新增协议仍需同步定义、生成产物与客户端。

```go
func (mole *Mole) CommandHandlers() map[runtime.CommandID]any {
	return map[runtime.CommandID]any{
		moleSnapshotPushCommand:          mole.handleSnapshotPush,
		moleBalanceCorrectionPushCommand: mole.handleBalanceCorrectionPush,
	}
}

func (mole *Mole) ProtocolHandlers() map[uint32]any {
	return map[uint32]any{
		uint32(demopb.MsgId_C2S_ENTER): mole.onEnter,
		uint32(demopb.MsgId_C2S_HIT):   mole.onHit,
	}
}
```

### 3.4 调用、超时与失败

- 按公开 Node、ServiceName、CommandID 和参数契约直接使用 GSR `Call/Send`。远程 Handler 使用 GSR 支持的规范参数类型，不另做内部 Protobuf 编解码；不为简单调用增加包装包或隐式重试。
- `Call` 必须有限等待，及时调用 `cancel` 释放上下文资源。等待会占用当前 Service 的处理边界，不能形成 A 等 B、B 又等 A 的循环；确需独立等待边界时才增加 Service。
- `Send` 成功只表示接纳。需要异步完成结果时，显式注册回执消息，并由业务 owner 定义请求关联、结果校验、超时、重复和迟到结果的处理。
- 框架负责运行和通信机制；哪些操作可重试、原操作身份、退避、补偿和恢复边界由业务决定。不要把这些策略藏在通用 RPC 包装或 Runtime 里。
- API 和注释说明成功代表提交还是完成，超时后操作是否可能继续；队列和待处理量设上限，重试需限频，并明确故障如何被观察和处置。

### 3.5 配置与外部依赖

- 配置通过明确结构体在加载边界完成默认值填充和校验，业务只接收最终配置，不在运行路径中重新读取文件、环境变量或命令行。
- 配置项较多时优先 Config 结构体；Functional Option 仅在可选项多、组合频繁且确实更清楚时采用。稳定的业务规则留在代码里，不为了灵活而过度配置化。
- 优先标准库。新增第三方依赖要说明实际用途，版本与生成工具固定，锁文件纳入版本管理；密钥和私密配置不提交。配置格式、路径与节点地址表规则见 [AGENTS.md](../AGENTS.md)。

## 4. 测试与验证

### 4.1 测试保护行为

- 每个 `Test...` 前写一句注释，说明它保护的可观察行为。测试关注输入、结果、状态和失败边界，不机械镜像私有方法。
- 新行为先建立关键失败用例；重构先确认已有相关覆盖，不重复验证 GSR 底层契约，也不为可逆、低影响的整理增加无意义测试。
- 新增并发或资源 owner 时，覆盖正常关闭、取消、超时和退出等待；涉及泄漏风险时验证资源最终释放。

### 4.2 按改动范围选择检查

下表是选择依据，不是每次依次执行的流水线。已有更完整验证覆盖同一份未变化代码时，不重复较窄的检查。

| 改动范围 | 需要的检查 |
| --- | --- |
| 纯文档 | diff、格式及相关链接，不运行 Go 测试 |
| 局部代码 | `gofmt` 与最小相关测试；有测试时不额外跑一次仅编译检查 |
| 完整组件、共享测试辅助代码或同包多个相关行为 | 受影响包的测试；静态分析对改动有价值时运行 `go vet` |
| 跨 module 收尾 | 在项目根目录执行 `./scripts/dev.sh check` |
| 并发、共享状态或生命周期变化 | 对受影响包追加 `-race`；不机械扩展到全仓 |
| 通信、存储或恢复能力验收 | 运行对应的真实 TCP、进程或数据库用例，不能以编译通过代替 |

Go 定向命令在对应 module 中执行，替换下例的包路径和测试名；工程脚本在 gsrdemo 根目录执行。仓库包含多个 Go module，根目录的 `go test ./...` 不能代替统一检查。

```shell
# 对应 module：局部验证，按需选择命令。
go test ./path/to/package -run '^TestSpecificBehavior$' -timeout=2m
go test ./path/to/package -timeout=5m
go test -race ./path/to/affected/package -timeout=5m
```

压力、泄漏和外部依赖测试可以由阶段验收或明确需求触发，但不能为了缩短日常检查，把普通正确性测试移出默认测试集。

### 4.3 耗时与结果说明

- 保留 Go 测试缓存，不习惯性运行 `go clean -testcache`；仅在排查缓存、随机性或 flaky 问题时使用 `-count=1`。外部依赖验收还需确认结果确实来自本次运行。
- 定向测试默认预算 2 分钟，包级测试默认 5 分钟；特殊集成或压力用例按已有入口与实际需要执行。`go test -timeout` 限制的是测试二进制运行时间，不是整个命令总耗时。
- 超时或长时间无进展时，先定位具体测试和等待点，不盲目重试，不靠增大 timeout 掩盖死锁或泄漏。明显偏离正常耗时也应检查原因。
- 互不争抢资源的检查可以并行；全仓测试与全仓 race 默认串行。只回收本次启动的进程。
- 汇报实际通过、未运行和未完成的项目；未运行真实通信或数据库用例时，不宣称对应能力已验收。

## 5. 评审建议

以下问题用于判断是否需要简化，不能只凭行数、层数或原则名称要求重构：

- **流程是否直白？** 读入口能否看清关键步骤；拆分是否减少理解成本，而不是增加转发和跨文件跳转。
- **状态是否集中？** 同一事实是否被多处保存，是否为重试、存储步骤增加了不必要的状态或重复布尔值。
- **边界是否清楚？** 调用者是否必须操作内部表、脏标记或清理顺序；隐藏细节后，成功、失败和资源归属是否仍然明确。
- **抽象是否必要？** 少量相似代码可以保留；提取公共逻辑前确认语义与变化原因相同，不因未来可能扩展而增加接口、泛型或回调。
- **等待是否隔离？** 慢 I/O 或单个热点是否阻塞无关业务；增加组件不能提供独立等待边界，需要结合 Service 和积压上限判断。
- **拆分是否有依据？** 出现独立变化的职责、过深嵌套或需要独立验证的规则时再拆；封装启动、停止和清理流程时保留原顺序、失败阶段及回滚语义。

工具通过只能证明相应检查通过，职责、命名和 API 的阅读成本仍需人工判断。
